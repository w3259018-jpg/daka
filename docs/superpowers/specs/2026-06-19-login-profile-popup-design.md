# 底部用户资料弹窗设计

## 目标

为“为一自在”微信小程序增加底部弹出式用户资料面板。静默登录保持不变；资料面板只负责补充昵称、解释资料用途，以及让用户选择完成资料或暂时以游客身份浏览。

## 已确认范围

- 采用 B“品牌引导式”布局：居中品牌标识、标题、副标题、默认头像、昵称输入、主按钮、跳过按钮和协议说明。
- 不自动读取微信头像或昵称，也不把隐私授权误作用户资料授权。
- 头像为空时展示“为一”默认头像；用户以后仍可在“我的”页面主动选择头像。
- 昵称由用户输入；确认时若昵称为空，生成并保存 `自在用户XXXX`，其中 `XXXX` 为四位随机数字。
- 资料是否完成只判断昵称，不再要求头像。
- 不修改后端接口，也不修改现有 `privacy-popup` 组件。

## 交互流程

### 首次进入

1. 应用继续通过 `wx.login` 完成静默登录。
2. 页面等待 `ensureLogin()` 完成后读取当前用户。
3. 用户没有昵称，且没有选择游客模式时，显示资料面板。
4. 遮罩不可点击关闭；用户必须确认资料或暂时跳过。

### 确认资料

1. 用户可输入昵称，也可留空。
2. 昵称为空时，客户端生成 `自在用户XXXX`。
3. 组件调用 `PUT /api/me/profile`，提交 `{ nickname }`。
4. 成功后更新 `app.globalData.user` 与本地 `user` 缓存。
5. 清除内存和本地存储中的 `guestMode`。
6. 组件触发 `profilesuccess` 事件，关闭面板；宿主页面刷新需要展示的用户数据。

### 暂时跳过

1. 设置 `app.globalData.guestMode = true`。
2. 将 `guestMode` 持久化到微信本地存储。
3. 组件触发 `skipsuccess` 事件并关闭面板。
4. 后续启动不自动重复弹出；用户浏览不受影响。

### 游客触发受限操作

1. 页面通过统一资料守卫检查当前用户昵称和游客状态。
2. 若资料未完成，显示“请先完善个人资料”。
3. 当前页面重新打开资料面板，而不是只给出无后续路径的提示。
4. 完成资料后，用户可重新执行原操作；系统不自动重放之前的写请求，避免误提交。

## 视觉设计

- 遮罩覆盖全屏，使用约 `rgba(0, 0, 0, .5)` 的半透明黑色。
- 面板固定在底部，背景 `#FFFDF9`，顶部圆角约 `32rpx`，包含底部安全区。
- 面板使用约 300ms 的自下而上进入动画。
- 顶部居中显示圆形“为一”品牌标识、标题“欢迎加入为一自在”和副标题“设置你的资料，开始打卡吧”。
- 默认头像为圆形暖色占位图，不使用微信头像权限。
- 昵称输入框使用 `type="nickname"`，占位文字为“输入你的昵称（可选）”。
- 主按钮为项目现有橙色渐变，文案“确认并开始使用”。
- 次按钮为橙色细边框，文案“暂时跳过”。
- 底部显示“继续即表示同意《用户协议》和《隐私保护指引》”，两段协议文字分别跳转现有页面。
- 提交中主按钮展示加载状态并禁用，防止重复请求。

## 代码结构

### `miniprogram/components/login-popup/`

组件负责渲染、输入状态、确认提交、跳过、协议跳转和事件通知。组件不判断具体页面业务权限。

组件状态：

- `visible`：控制遮罩和面板。
- `nickname`：用户当前输入。
- `loading`：阻止重复确认。

组件事件：

- `profilesuccess`：资料保存成功，携带 `{ user }`。
- `skipsuccess`：用户选择游客模式。

### `miniprogram/utils/profile-guard.js`

统一封装以下纯逻辑和状态操作：

- 判断用户是否已有昵称。
- 判断是否应在启动后自动显示面板。
- 判断写操作是否需要资料拦截。
- 生成 `自在用户XXXX`。
- 持久化或清除游客模式。
- 更新全局用户和本地用户缓存。

页面负责在拦截结果为真时设置 `showLoginPopup`，确保守卫不依赖页面实例。

### 页面接入

所有需要自动展示或重新打开面板的页面注册同一组件，并提供统一的成功/跳过回调。首个 Tab 页面负责首次进入时的自动展示；其他页面在受限操作触发时展示。

受限写操作包括：

- 创建任务。
- 通过邀请码加入任务。
- 发布打卡内容。
- 标记内容已观看。
- 提交打卡心得。
- 导出本人记录或管理员数据。
- 管理员修改成员角色、移除成员或解散任务。

普通页面浏览、任务详情查看、媒体播放本身不受限制。媒体播放不会在游客状态下写入“已观看”记录。

## 数据与兼容性

- `guestMode` 在 `app.globalData` 和微信本地存储中保持一致。
- 应用启动时无论是否存在缓存 token，都读取 `guestMode`，避免不同登录分支状态不一致。
- 静默登录返回用户后不自动覆盖游客选择。
- 资料保存成功后，将接口返回用户与现有全局用户合并，并同步本地缓存。
- “我的”页面成功保存昵称后同样清除游客模式。
- 头像字段为空属于有效状态；所有头像展示位置应有默认头像回退。

## 错误处理

- 资料提交失败时保留弹窗、昵称输入和游客状态，恢复按钮并使用现有 `request()` 错误提示。
- `loading` 状态阻止连续点击造成重复资料请求。
- 随机昵称生成后以接口成功为准；接口失败时不提前修改全局用户。
- 本地存储写入使用小程序同步存储 API，与项目现有 token/user 缓存方式一致。
- 被拦截的业务操作不会自动重放，用户完成资料后需再次明确点击。

## 测试策略

- 为资料守卫增加 Node 可运行的单元测试，覆盖空昵称生成、已有昵称保留、自动弹出判断、游客拦截和游客状态清理。
- 为组件逻辑增加轻量 VM 测试，验证空昵称提交、接口失败、重复确认、事件触发和跳过持久化。
- 扩展或复用 `check-miniprogram.js`，验证组件注册、引用文件存在、JSON 合法、JS 可编译和 WXML 非空。
- 运行全量小程序静态校验，要求结果为 `0 failed`。
- 在微信开发者工具中人工检查首次弹出、底部安全区、昵称键盘、协议跳转、游客再次触发和资料完成后的关闭状态。

## 非目标

- 不新增手机号登录。
- 不申请或静默读取微信头像、微信昵称。
- 不新增后端字段或接口。
- 不修改现有隐私授权组件。
- 不自动执行用户在资料完善前尝试的写操作。
